# Plan: Detect drives and mounts automatically, add favorite paths
Intent: [intent.md](intent.md). Status: accepted.
Branch: feature/28-detect-mounts-favorites

## Design

- **Host root.** New config `HostRoot:Path`: `/hostfs` in `appsettings.json`, `/` in `appsettings.Development.json`.
  `HostRootService.IsUnderHostRoot(path)` replaces `AllowedRootsService.IsAllowed` (same normalize + prefix logic, moved).
- **Mount table.** `IMountTable` in Core: `IReadOnlyList<MountInfo> GetMounts()` and `MountInfo? FindContaining(string path)`
  (longest mount point that is the path or its ancestor). `MountInfo(string MountPoint, string FileSystemType, bool IsReadOnly)`.
  - `LinuxMountTable` reads `/proc/self/mountinfo` on every call (no cache; a new drive shows without restart).
    Field 5 is the mount point, field 6 the mount options (`ro` or `rw` first), the filesystem type is the first field after ` - `.
    Unescape `\040` (space), `\011`, `\012`, `\134`. Parsing is a static method `Parse(string text)` so tests feed fixture text.
  - `FallbackMountTable` for non-Linux dev (macOS): `DriveInfo.GetDrives()` with `DriveType` Fixed, Removable or Network; all read-write.
  - Registered by `OperatingSystem.IsLinux()` in `Program.cs`.
- **Detected mounts** (`MountDetectionService.GetScanRoots()`): mounts under the host root whose filesystem type is in
  `ext2 ext3 ext4 xfs btrfs zfs ntfs ntfs3 fuseblk exfat vfat hfsplus apfs nfs nfs4 cifs smb3`,
  excluding mount points under `<hostRoot>/boot`, `<hostRoot>/snap`, `<hostRoot>/var/lib/docker`, `<hostRoot>/run`, `<hostRoot>/proc`, `<hostRoot>/sys`.
  Label = mount point with the host root prefix removed, `/` when empty. Sorted by mount point.
  On macOS the fallback returns drives under `/` and `/Volumes`; the filesystem type filter is not applied there.
- **Favorites.** New entity `FavoritePathEntity` (`Id` Guid, `Path` string unique, `Label` string, `CreatedAt` DateTimeOffset),
  table `FavoritePaths`, migration `AddFavoritePaths`. API `api/favorites`: `GET`, `POST {path, label}`, `PUT {id} {label}`, `DELETE {id}`.
  `POST` stores `Path.GetFullPath(path)` and rejects (400) a path that is not under the host root, not an existing directory,
  or already a favorite (409). An empty label defaults to the path without the host root prefix. `PUT` changes only the label.
- **Roots API.** `GET api/roots` returns `ScanRootDto(string Path, string Label, string Kind, bool AllowDelete)`,
  `Kind` = `"mount"` or `"favorite"`: detected mounts first, then favorites ordered by label.
  `AllowDelete` = `!IMountTable.FindContaining(path).IsReadOnly`. A favorite whose directory no longer exists is still listed.
- **Delete.** `PathSafetyValidator` takes `IMountTable` and `HostRootService` instead of `AllowedRootsOptions`.
  All current checks stay, in the same order. The last check changes: the resolved candidate must be under the host root,
  and its containing mount must be read-write. Error texts: "Path is outside the host root." and "Path is on a read-only mount.".
- **Frontend.** `AllowedRoot` becomes `ScanRoot` (`path`, `label`, `kind`, `allowDelete`).
  The drop-downs on scan-start and schedules show two `mat-optgroup`s: "Drives and mounts" and "Favorites".
  Scan-detail `canDelete` = some root with `allowDelete` whose path is the scan root, an ancestor of it, or a descendant of it,
  compared on whole path segments (`/a/b` does not match `/a/bc`). The backend still decides per file.
  New page `features/favorites/` at route `favorites`, nav link "Favorites" after "Schedules": a table (label, path, actions)
  with inline label edit and delete, and an add form (path input, optional label). Server errors show under the form.
  Service `core/services/favorite.service.ts`.

## Risks
- **Riskiest: step 2 (delete check).** Deletion moves from an explicit allow-list to "any read-write mount under the host root".
  A deployment that mounts something `:rw` under `/hostfs` without meaning to allow deletes now allows them. The README must say this.
- Parsing mistakes in `mountinfo` (escaped spaces, optional fields before ` - `) would hide drives or misreport `ro`/`rw`.
  A misread `rw` on a read-only mount is not destructive: the OS still refuses the delete.
- Existing schedules and scans keep their `RootPath` even if it is outside the new host root. Schedules still run (no run-time check today, none added);
  editing such a schedule will be rejected until its root is changed.
- Your deployment's `AllowedRoots__*` env vars become unused; nothing breaks, but the drop-down content changes.
- macOS dev: the fallback treats every drive as read-write, so the UI shows delete on the system volume in dev.
